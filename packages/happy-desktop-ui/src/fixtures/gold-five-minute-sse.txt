Server-sent events let a server keep an HTTP connection open and send new messages to the browser whenever data becomes available. The browser starts the connection with the `EventSource` API, which behaves much like making a normal request but continues listening instead of expecting the response to end. Messages arrive as UTF-8 text in a simple line-based format, usually with fields such as `data`, `event`, and `id`. Each event is separated by a blank line, allowing the browser to recognize complete messages as the stream flows.

The connection is one-way, carrying updates from the server to the client while ordinary HTTP requests handle communication in the other direction. This makes server-sent events well suited to status feeds, notifications, live dashboards, and streamed text responses. Servers typically send a `Content-Type` of `text/event-stream` and flush output promptly so intermediaries do not hold messages in a buffer. Because the protocol runs over regular HTTP, it often fits existing infrastructure more easily than a custom persistent transport.

Browsers automatically reconnect when an SSE connection drops, which gives the mechanism useful resilience with little application code. A server can include event identifiers so a reconnecting client reports the last event it received and avoids missing later updates. It can also suggest a retry delay to control how quickly reconnection attempts occur. SSE does not carry binary frames directly and is less flexible than WebSockets for fully interactive, bidirectional traffic, but its simplicity is a major advantage for server-to-client streams.
